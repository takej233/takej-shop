# takej 商城

一个基于 Spring Cloud 微服务架构的电商系统，包含**商城前台**和**后台管理**两套完整的前后端实现。

后端按业务边界拆分为 7 个独立服务，通过网关统一对外；前端使用 Vue 3 组合式 API + TypeScript，商城与后台共用一套请求层、两套独立登录态。

## 功能清单

### 商城前台

- **注册 / 登录**：注册后自动创建默认用户资料；注册成功需再登录（接口不自动登录）
- **商品浏览**：商品列表（按 `sort` 倒序）、商品详情、已下架商品优雅提示
- **购物车**：加入 / 改数量 / 勾选 / 删除单项 / 批量删除已勾选；重复加购自动累加数量；**已下架商品自动取消勾选并标记**
- **下单**：支持「购物车结算」和「立即购买」两条路径
- **订单**：订单列表、订单详情（含下单时的商品名称与价格快照）、支付、取消、确认收货
- **个人资料**：查询与修改，资料缺失时自动补建

### 后台管理

- **管理员登录 / 退出**：登出会立即失效服务端会话
- **权限驱动 UI**：按权限码动态显示按钮
- **商品管理**：列表（含下架与已删除商品）、新增、编辑、上下架、逻辑删除
- **库存管理**：增量式调整库存 + 库存变动流水（区分人工调整 / 下单扣减 / 订单归还）
- **订单管理**：全部用户订单列表、订单详情、关闭待支付订单（自动归还库存）
- **操作日志**：记录所有改变系统状态的管理动作

## 技术亮点

### 1. 网关统一鉴权与两套身份体系

系统有**两套完全独立的登录体系**（商城用户 `USER` 与后台管理员 `ADMIN`），Token 存在不同的 Redis key 前缀下，**互相不能调用对方的接口**。

网关在放行前完成三件事：

1. 校验 JWT 签名与有效期
2. 校验 Redis 中登录会话是否存在（支持服务端主动失效，如管理员登出）
3. 按 Token 里的 `principalType` 分流，**清除客户端伪造的身份请求头**，再注入真实身份

因此下游服务只需信任 `X-User-Id` / `X-Admin-Id`，不必各自解析 JWT，也不用担心请求头被伪造。

### 2. 下单的跨服务库存补偿

下单流程涉及跨服务调用（订单服务 → 商品服务扣库存），`@Transactional` 只能回滚订单库，**回滚不了已经提交的远程扣减**。

实现方式：逐件扣减时记录"已成功扣减的商品"，任一环节失败就**逆序调用商品服务把库存加回去**，再抛出异常让本地事务回滚。

同理，订单取消 / 超时关闭 / 管理员关单三条路径都会归还库存，并通过**条件更新抢占**保证库存只会归还一次。

### 3. 下单幂等

用户重复点击、网络重试都可能触发重复下单。实现方式：

- 前端每次点击生成一个 `requestId`（UUID），随请求提交
- 后端在**业务方法最开头**查 `takej:order:idempotent:{userId}:{requestId}`
  - 命中 → 直接返回首次创建的订单 ID，不重复扣库存
  - 未命中 → 正常创建，**成功后才写入标记**（TTL 10 分钟），失败不写，允许重试
- 幂等逻辑对 Redis 故障**降级处理**：缓存不可用时只记日志，不阻断下单

### 4. 库存的原子扣减与审计流水

扣减库存使用一条带条件的 SQL，把"判断库存是否足够"和"扣减"合并为原子操作，避免并发超卖：

```sql
UPDATE product
SET stock = stock - #{quantity}
WHERE id = #{id} AND status = 1 AND deleted = 0 AND stock >= #{quantity}
```

每次库存变动都会在同一事务内写入 `product_stock_log`，记录来源、变动前后值、操作人，形成可追溯的审计流水。

### 5. 前端请求层的统一收口

- **两个 Axios 实例**分别绑定商城与后台的 Token key，互不干扰
- **401 与 403 严格分流**：401 表示身份不被承认（清登录态跳登录页），403 表示身份有效但权限不足（留在原页提示）
- 后端返回的中文业务提示**直接透传给用户**，前端不再二次包装
- 金额一律用**整数分**计算，避免浮点误差

## 快速开始

### 前置依赖

- JDK 17
- Maven 3.9+
- Node.js 20+
- MySQL 8.0（运行在 `3306`）
- Redis（运行在 `6379`）

### 1. 准备数据库

需要创建 6 个库：`takej_auth`、`takej_user`、`takej_product`、`takej_cart`、`takej_order`、`takej_admin`。

> 各库的表结构未纳入版本库（本地配置被 `.gitignore` 忽略）。可从现有数据库用 Navicat 的「转储 SQL 文件」导出 `schema.sql` 补进仓库。

### 2. 配置后端

每个服务在 `src/main/resources/` 下有：

- `application.yml`：端口、服务名（已入库）
- `application-local.yml`：**数据库连接、Redis、JWT 密钥（未入库，需自行创建）**

`application-local.yml` 里需要的配置项：

```yaml
spring:
  config:
    activate:
      on-profile: local
  datasource:
    url: jdbc:mysql://localhost:3306/<本服务对应的库>
    username: <你的账号>
    password: <你的密码>

takej:
  jwt:
    secret: <至少 32 位，必须与网关完全一致>
    expire-seconds: 72000
```

> `mall-gateway`、`mall-auth`、`mall-admin` 的 `takej.jwt.secret` **必须完全相同**，否则 Token 无法通过网关校验。

### 3. 初始化管理员账号

在 `mall-admin` 的 `application-local.yml` 中临时加上：

```yaml
takej:
  admin:
    bootstrap:
      enabled: true
      username: admin
      password: admin123   # 至少 6 位
```

启动 `MallAdminApplication`，日志出现「管理员初始化成功」后，**建议把 `enabled` 改回 `false`**（该逻辑是幂等的，同名会跳过）。

### 4. 启动后端

按顺序启动（网关可以最后）：

```
MallAuthApplication       9001
MallUserApplication       9002
MallProductApplication    9003
MallCartApplication       9004
MallOrderApplication      9005
MallAdminApplication      9006
MallGatewayApplication    8080
```

自检：

```bash
curl http://localhost:8080/health
# {"code":0,"message":"success","data":"mall-gateway is running"}
```

### 5. 启动前端

```bash
cd frontend
npm install
npm run dev
```

打开 `http://localhost:5173`。

> 前端通过 Vite 代理把 `/api/**` 转发到网关 `8080`，浏览器看到的是同源请求，因此**不需要后端配置 CORS**。

### 6. 访问入口

| 入口 | 地址 |
|---|---|
| 商城前台 | `http://localhost:5173/` |
| 商城注册 | `http://localhost:5173/register` |
| 后台管理 | `http://localhost:5173/admin/login` |

## 接口约定

### 统一响应结构

除网关自身的 401 外，所有业务接口返回同一结构：

```json
{ "code": 0, "message": "success", "data": {} }
```

### HTTP 状态码即业务错误码

| 状态码 | 含义 | 前端处理 |
|---|---|---|
| `400` | 参数不合法 | 提示 `message` |
| `401` | 未登录 / Token 失效 / 账号被禁用 | 清 Token 并跳登录页 |
| `403` | 已登录但权限不足 | **原地提示**，不跳登录页 |
| `404` | 资源不存在（如商品已下架） | 提示「已下架」 |
| `409` | 状态冲突（库存不足、用户名已存在、订单状态不允许操作） | 提示 `message` 并刷新数据 |
| `500` | 服务端异常 | 提示「服务异常，请稍后重试」 |

**401 与 403 必须分开处理**：把 403 也当成登录失效，会导致用户点一个没权限的按钮就被踢回登录页。

### 请求头规则

```http
Authorization: Bearer {token}
```

`X-User-Id` / `X-Username` / `X-Admin-Id` / `X-Admin-Username` 由网关注入，**客户端不要手动传递**——网关会先清除伪造值再写入真实值。

## 开发中解决的关键问题

以下问题都是在前后端联调时才暴露的，记录在这里作为技术积累。

### 1. 全量更新导致数据被静默清空

后台编辑商品时，只改了价格，结果商品的副标题和主图变成空值。

**原因**：后台列表的 DTO 只暴露了 6 个字段，前端拿不到副标题和主图，编辑表单回填为空；而更新接口是**全量更新**，于是把 `null` 写进了数据库。

**启示**：列表 DTO 与详情/编辑所需的字段不一致时，全量更新就是数据破坏的入口。要么保证字段完整，要么改用部分更新。

### 2. 幂等检查的位置决定它是否真的生效

最初把幂等判断写在 `createOrder` 里，而购物车结算方法在调用它之前会先校验"购物车有没有已勾选商品"。

**现象**：重复提交时，购物车已被第一次清空，请求死在「没有选中商品」的 400 上，**根本走不到幂等判断**。看起来像幂等没生效，实际上它压根没被执行。

**启示**：幂等检查必须放在业务方法的**最开头**，早于一切业务校验。位置一旦被后续校验挡在前面，幂等就形同虚设。

### 3. 无状态 JWT 的会话失效边界

用户登录后拿到 Token，此后管理员把他禁用（`status = 0`），该用户手里的 Token **在有效期内依然可用**。

**原因**：登录时会校验账号状态，但网关后续只校验 JWT 签名和 Redis 会话，**不回查用户表**。这是无状态 Token 的固有特性——签发了就自带授权。

**同类问题**：用户改密码后，旧 Token 同样继续有效。

**可选方案**：
- 登录时维护「用户 → 其所有 Token」的索引，禁用时清空该用户全部会话（不用改网关）
- Redis 存禁用名单，网关每次请求多查一次（更通用，但增加每请求开销）

### 4. 跨服务事务的补偿边界

`@Transactional` 只能回滚本地库，对跨服务的 HTTP 调用无效。因此下单失败时必须**显式补偿**已扣减的库存，否则会出现"库存扣了但订单没建成"的超卖问题。

本项目暂未引入 MQ 或分布式事务框架，采用**同步调用 + 显式补偿 + 幂等标记**的组合。真正的最终一致性方案需要在生产环境中评估。

## 已知限制

| 限制 | 说明 |
|---|---|
| Token 不随禁用立即失效 | 见「开发中解决的关键问题」第 3 条 |
| 无支付回调 | `POST /api/orders/{orderId}/pay` 是模拟支付，直接改状态 |
| 列表接口无分页 | 订单与操作日志硬编码 `LIMIT 100`，商品列表返回全部 |
| 后台缺少用户管理 | 无法在后台查看或管理商城用户 |
| 操作日志无操作人姓名 | 只记录 `adminId`，需要额外接口才能显示用户名 |
| 商城用户无退出接口 | 前端只清本地 Token，服务端会话在 20 小时内仍有效 |
